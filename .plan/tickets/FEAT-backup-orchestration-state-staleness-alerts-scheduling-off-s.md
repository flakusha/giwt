## Summary

Problem: the dump engine (L0 FEAT-backup-command-family) and the annex passthrough (L1 FEAT-git-annex-passthrough) need an orchestration layer: durable job state, staleness alerting, scheduling, and off-site transfer — the researched B3+B6 scope (loop-lore scratchpad open-items-alignment, DistributedSync.md sync-daemon).

Scope:

- Durable state: JSONL state ledger (sibling of `.ledger.jsonl`, e.g. `<treeDir>/.backup.jsonl`) recording per-remote events `{ts, kind: dump|sync|copy|verify, remote, path, type full|incr, size, sha256, verifiedAt, offsiteAt}`; `giwt backup status` renders last success per kind/remote.
- Staleness: `--staleness <dur>` (default 24h) — warn line in status alert, exit 1 under `--strict` so cron/systemd sees failures; noted in ledger as alerts.
- Scheduling: documented systemd timer + cron units generated by `giwt backup schedule --dry-run` (emits unit snippets pinned to this giwt binary path, matching run-record retention).
- Off-site: `giwt backup remote --target rclone|rsync|ssh` — rclone copy / rsync -az / ssh stream; mesh-VPN discovery: read tailscale `tailscale status --json` peer hostnames and offer MagicDNS candidates as remote names (best effort, `--discover`).
- Distributed property: because git + git-issue already live in the repo's object store, annexing + dumping the repo backs up its plans + issue history by construction — no separate sync protocol for the ticket layer (the key synergy from the giwt integration review).
- Fsck annexation: `giwt backup status --annex` shows repo-level `git annex whereis`/`unused` counts through the read-only policy rows.

## Possible Caveats and Issues to Avoid

- TOCTOU: state ledger appends from concurrent agents — append with single fsync write, never rewrite in place.
- Security: remote targets carry credentials in crontab-era env — never print secrets; reference env var NAMES in units only.
- Authorization: remote sync must never delete server-side beyond `--prune` opt-in; rsync `--delete` refused unless explicitly configured.
- Partial failure: mark event failed before exit code lands (beacon write), so staleness sees truth; failed verify never advances offsiteAt.
- Idempotency: repeated schedule dry-runs byte-identical.
